Initial internal EFI staging (2026-10-21)
=======================================

Maintained tool contract below; dated physical sections afterward are history.
Current recorded baseline: README.md (entry0003, EFI/Riplix-gui as of the
2026-10-22 reconciliation). SSH: ssh.md. Repeated candidate publication:
efi-updates.md uses a fresh namespace per candidate with this same tool.
It does not turn apply into an in-place updater.

tools/x86_64/internal_boot.py stages an initial Riplix trial on an explicitly
selected, already mounted ESP. It does not discover disks, mount partitions,
run efibootmgr, change BootOrder/BootNext, reboot, or copy the root filesystem.
The platform owner must separately verify the physical disk/PARTUUID and the
selected mount directory. --esp-id records that caller-verified identity; the
tool cannot establish it from a directory pathname.

Inputs are two distinct AMD64 PE32+ EFI applications and independently supplied
SHA256 hashes: candidate and previously accepted known-good. Structural PE
validation and matching hashes do not establish that an image boots on the HP.
The caller chooses those hashes from accepted build/hardware evidence.

Initial files, all owned by this tool:
  EFI/Riplix/BOOTX64.EFI     Candidate for a separately configured one-boot trial.
  EFI/Riplix/BOOTGOOD.EFI    Independently checked fallback, selected manually
                           by firmware/file browser if needed.
  EFI/Riplix/manifest.json  Exact paths, sizes, SHA256, PE metadata, stage time,
                           caller ESP identity; never claims boot acceptance.

--directory Riplix-tui selects an independent initial-stage namespace instead
of the default Riplix. Both apply and inspect require the same selection; paths
in the manifest and interrupted-stage prefixes follow it. Names must be exactly
Riplix or Riplix- followed by1 to48 ASCII letters/digits/hyphens, starting with a
letter or digit. Existing other namespaces remain untouched; this does not
enable replacement or firmware selection. New candidates can be published in
fresh namespaces; the maintained procedure is efi-updates.md.

No EFI/ubuntu, EFI/BOOT or recovery payload is replaced. There is no full ESP
backup and no private key/root image copy. The known-good EFI uses its embedded
root selection policy; it is not a rollback of the installed root filesystem.
The fallback file alone does not automatically rescue a hung candidate.

Example argument shapes (replace every uppercase value with independently
verified input; neither example changes firmware state):

  python3 tools/x86_64/internal_boot.py apply --esp-dir ESP_MOUNT \
    --esp-id PARTUUID=VERIFIED_ESP_PARTUUID \
    --candidate CANDIDATE.EFI --candidate-sha256 CANDIDATE_SHA256 \
    --known-good ACCEPTED.EFI --known-good-sha256 ACCEPTED_SHA256

  python3 tools/x86_64/internal_boot.py inspect --esp-dir ESP_MOUNT \
    --esp-id PARTUUID=VERIFIED_ESP_PARTUUID \
    --candidate-sha256 CANDIDATE_SHA256 --known-good-sha256 ACCEPTED_SHA256 \
    --manifest-sha256 SHA256_RETURNED_BY_APPLY

Each file is exclusively created, completely written, fsynced and read back.
The directory and parent directory are fsynced; the complete directory is then
published atomically with no-replace semantics and re-verified. Native host
support is required: Linux renameat2(RENAME_NOREPLACE), or macOS
renamex_np(RENAME_EXCL). Publication fails closed on unsupported filesystems or
failed fsync. A failed post-publication check retains the destination for
inspection, never silently overwriting or rolling it back.

A clean repeat with the same hashes verifies and fsyncs existing files without
rewriting them, completing synchronization after a prior final-fsync failure.
Any missing/unrecognized/rejected file state or different hashes is
refused. This initial-staging tool intentionally provides no update/promotion
or deletion command. Unexpected case-colliding names and symlinks are refused.

Interruption before directory publication may leave an EFI/.Riplix-stage-*
directory. inspect reports these names; apply refuses to proceed until the
owner reviews them. Ordinary write/space failures clean only the unique staging
directory made by the current invocation. Abrupt interruption and a failure
after publication preserve evidence. Do not create firmware entries or select
BootNext until apply/inspect succeeds, the exact manifest is recorded, and the
parent's device identity/Ubuntu-preservation checks pass. Keep USB recovery.

Offline validation:
  python3 tools/x86_64/tests/test_internal_boot.py

Tests cover exact manifest/readback, unrelated Ubuntu/BOOT/recovery hashes,
idempotent verification, malformed PE and hashes, symlinks/nonregular sources,
unknown/rejected states, insufficient space and write failure, corruption,
interruption, and a destination appearing during atomic publication. They use
temporary directories only, not disks, mounted ESPs or firmware variables.
