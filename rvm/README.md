# RVM - Ripple Virtual Machine

A reference implementation of the Ripple VM architecture that executes programs produced by the ripple-asm assembler and linker.

## Features

- Complete implementation of all Ripple VM instructions
- Support for all 32 registers
- 16-bit cell width with wrap-around arithmetic  
- Configurable bank size (default: 4096)
- Memory-mapped I/O for output
- Debug mode for step-by-step execution
- Binary program loader (RLINK format)

## Instruction memory

Instruction storage grows lazily, with a default ceiling of 67,108,864
instructions (512 MiB of decoded instructions, plus JIT memory). Use
`--code-memory N` to change this ceiling in instruction units. The same budget
applies to binary loading, STORC and bulk uploads; it is independent of data
RAM's `--memory` setting. The MEMORY_INFO device command reports the available
capacity. Library users can call `VM::set_code_memory_limit` before loading.

## Execution and display performance

By default, Ctrl-C stops an interactive VM. `--guest-ctrl-c` instead delivers
ASCII ETX to the guest TTY, allowing an operating system to interrupt foreground
programs. In that mode, Ctrl-] remains an emergency host stop. The FUZIX launcher
selects this mode automatically; `shutdown` remains its clean way to stop.

Normal CLI execution batches up to the next 1,024-instruction host-poll boundary.
The batch stops earlier at a bank-zero MMIO write, HALT, BRK, execution error,
or the exact instruction budget. Tick grants and frame capture remain controlled
by the runner. Instructions are still fetched individually, so `STORC` changes
take effect immediately; IRQ dispatch still occurs before each instruction.
The ISA, binary format, guest instruction counts, and device interface are unchanged.

Debugging, verbose traces, and instruction-frequency throttling use single-step
execution. Library users can compare `runner::run` with `runner::run_reference`
using the same `RunOptions` and binary. `VM::run_batch` is a lower-level operation:
its caller must handle pending ticks, capture, host polling, and limits.

The RGB565 window shares immutable completed frames with the VM. It converts a
frame only after a presentation or layout change, outside the display mutex;
expose and window-resize events can redraw the cached image. Window-close polling
uses an atomic flag. Both the legacy double buffer and extended display keep
completed frames independent of later guest writes.

Run the execution-boundary and device regressions with `cargo test -p rvm`.
For application measurements, `ports/doom/tools/benchmark.mjs` records headless
production-runner times and checks every frame against native C. Compare the
same guest binary to isolate VM gains; compare guest instruction counts to
measure compiler gains. Headless timings do not measure window contention.

## JIT execution

Use `rvm program.bin --jit --report run.json`. Debugging, verbose traces, and
instruction-frequency throttling retain the interpreter.

The JIT interprets cold code and compiles an entry after 1,024 visits. Discovery
uses a deterministic work queue and stops at existing compiled code. Regions
contain at most 64 basic blocks, each containing at most 32 instructions. Their
entry dispatcher uses jump tables or a search tree. A single budget guard per
basic block keeps the exact batch limit; short batch tails use the interpreter
until they reach a published native entry. Covered interiors do not trigger
another translation of the same instructions.

Guest registers and counters stay in native variables and are published at
calls, exits, and faults. Only registers a region can modify need writeback.
Nonzero data banks use checked native memory accesses. Bank zero retains the
reference MMIO and legacy-display handlers, and invalid memory accesses retain
the reference diagnostics. The data-memory pointer is refreshed at batch entry.

Non-linking JALs are jumps. Linked calls can invoke cached native code, with a
64-frame depth limit; deeper guest calls continue through the driver. Missing
callees also return to the driver, so compilation never runs on a live native
call stack. STORC
invalidates covering regions and changes an epoch that makes active callers
unwind before resuming stale code. Retired native memory is reclaimed only after
returning to the driver, explicitly releasing Cranelift executable allocations.
Loading another image clears every published call slot.

The ISA and RLINK format are unchanged. Software floats still execute the same
16-bit integer instruction sequences, including their existing rounding and
special-value behavior. These changes require no additions to the Brainfuck VM.

Reports include a `jit` object with cumulative compiled-region and instruction
counts, generated native bytes, total and maximum compilation milliseconds,
and interpreted/native guest-instruction counts. Generated bytes are cumulative,
including code later invalidated. These timings include native compilation and
finalization, but exclude the language frontend and assembler/linker.

The original implementation already reused the interpreter's device handlers,
tracked instruction budgets, and invalidated self-modifying code. Its main
problems were eager compilation of one-shot initialization, repeated rescanning
of discovered instructions, one instruction per block, a linear entry-dispatch
chain, duplicated invalidation maps, and repeated VM-state bookkeeping. Native
calls for non-linking jumps and uncleared call slots after image reload were
also correctness problems. Dropping a Cranelift module without explicitly freeing
its executable memory also made the old reclamation ineffective. The emitter is now separated into region discovery,
host helpers, arithmetic, memory, and control-flow code. Tests force native
translation independently of warmup so small fixtures exercise the emitter.

Compare an unchanged binary with:

```bash
python3 rvm/tools/benchmark_jit.py ports/doom/build/ripple/engine/engine.bin \
  --frame 1 --runs 3 --output /tmp/doom-jit.json --vm-args \
  --bank-size 64000 --memory 16384000 --disk ports/doom/build/run/doom1.wad \
  --seed 1 --clock unthrottled
```

Add `--baseline /path/to/previous/rvm` before `--vm-args` to include the old JIT.
For a compute-only program, omit `--frame`; `--skip-interpreter` compares just JIT
versions when an interpreter run would dominate the experiment. The tool copies
disks per run, includes process startup and JIT compilation in elapsed time,
and compares successful runs' output hashes, frame bytes, and instruction counts.
It records timeouts explicitly instead of treating partial runs as completed work.
For moving and shooting in the current title binary, capture a later frame and
append `--input-script ports/doom/tests/jit-gameplay.json` to the VM arguments;
that script opens the menu and starts a game before sending gameplay controls.

Release measurements on 2026-10-15 (headless, unthrottled, median of three
fresh processes; native compilation included):

| Workload | Reference | Revised JIT |
| --- | --- | --- |
| Full Beep, 44,100 samples | Previous JIT: 17.965 s | 8.116 s |
| Current Doom, first title frame | Interpreter: 0.408 s | 0.879 s |
| Current Doom, scripted gameplay through frame 180 | Interpreter: 7.044 s | 4.108 s |

The previous JIT failed to reach Doom's first frame with a 15-second limit: it
returned the timeout after 19.8 seconds and only 262,144 instructions. The
interpreter and revised JIT both reach that frame after 36,927,898 instructions.
Cold JIT startup still costs more than interpreting this short title workload.
The gameplay comparison uses the current cooked-WAD binary, full 320×200
resolution, seed 1, and `ports/doom/tests/jit-gameplay.json`. All successful comparison runs
match guest instruction counts, stdout hashes, and captured frame bytes.
The full Beep comparison also matches all 391,700 output bytes and exactly
7,154,129,521 guest instructions. Window contention is outside these measurements.

The remaining software-sine cost is the same large sequence of integer guest
operations: notably multiword software division and multiplication. Improving
those integer algorithms or their frontend lowering would also benefit the
Brainfuck implementation. The JIT improvements above reduce host overhead
without replacing those guest operations with host floating-point math.

## Usage

```bash
# Run a binary program
rvm program.bin

# Run with verbose output
rvm -v program.bin

# Run in debug mode (step-by-step)
rvm -d program.bin

# Specify custom bank size
rvm -b 4096 program.bin

# Specify custom memory size (in words)
rvm -m 32768 program.bin

# Or use cargo run
cargo run --release -- program.bin
```

### Debug Mode Commands

When running with `-d` (simple debugger), the following commands are available:
- **Enter** - Step one instruction
- **r** - Run to completion
- **c** - Continue from breakpoint (after BRK)
- **q** - Quit debugger

## TUI Debugger Mode (-t)

The TUI (Terminal User Interface) debugger provides a professional debugging environment with multiple synchronized panes and advanced features.

### Launch
```bash
rvm -t program.bin
```

### Interface Layout
The TUI debugger displays 6 panes simultaneously:
1. **Disassembly** (F1) - Shows instructions with addresses, breakpoints, and current PC
2. **Registers** (F2) - All 18 registers with change highlighting
3. **Memory** (F3) - Hex and ASCII view with editing capabilities
4. **Stack** (F4) - Return address tracking
5. **Watches** (F5) - Named memory locations for monitoring
6. **Output** (F6) - Program output buffer

### Navigation
- **F1-F6** - Switch directly to specific pane
- **Tab** - Cycle through panes forward
- **Shift+Tab** - Cycle through panes backward
- **h/j/k/l** - Vim-style navigation within panes
- **↑/↓/←/→** - Arrow key navigation
- **PageUp/PageDown** - Scroll by page in current pane

### Execution Control
- **Space/s** - Step single instruction
- **r** - Run until breakpoint or halt
- **c** - Continue from current breakpoint
- **R** - Restart execution from beginning (preserves program)

### Breakpoints
- **b** - Toggle breakpoint at cursor position
- **Shift+B** - Set/toggle breakpoint by instruction number
  - Enter instruction number (e.g., "5" for instruction #5)
  - Or hex address (e.g., "0x100")
- **B** - Clear all breakpoints

### Memory Operations
- **g** - Go to memory address (enter hex address)
- **a** - Toggle ASCII display in memory pane
- **e** - Edit memory with multiple formats:
  - `addr:0xFF` - Hexadecimal value
  - `addr:255` - Decimal value
  - `addr:'A'` - Single character
  - `addr:"Hello"` - String (writes multiple bytes)
  - `addr:0b1010` - Binary value
- **0-9,a-f** - Quick hex edit at cursor (Memory pane only)
- **w** - Add memory watch (format: `name:address[:format]`)
- **W** - Remove selected watch

### Command Mode (:)
Press `:` to enter command mode for advanced operations:
- `:break <addr>` - Set breakpoint at address
- `:delete <addr>` - Remove breakpoint at address
- `:watch <name> <addr>` - Add named memory watch
- `:mem <addr> <value>` - Write value to memory
- `:reg <#> <value>` - Set register value
- `:help` - Show help
- `:quit` or `:q` - Exit debugger

### Other Keys
- **?** - Toggle help overlay
- **q** - Quit debugger (also available in command mode)
- **ESC** - Cancel current input/mode

### Visual Indicators
- **Breakpoints** - Red `●` markers in disassembly
- **Current PC** - Yellow highlighted line with `►` marker
- **Register changes** - Yellow highlighting for recently modified registers
- **Non-zero values** - White text for non-zero memory/registers
- **I/O registers** - Magenta highlighting for addresses 0x0000-0x0001
- **Active pane** - Cyan border and "ACTIVE" label

### Memory Display Features
- 16 bytes per row in hexadecimal
- Optional ASCII representation (toggle with 'a')
- Color coding for special addresses and non-zero values
- Continuous scrolling through entire memory space

### Tips
- Use Shift+B to quickly set breakpoints at specific instructions
- Memory edits support various formats for convenience
- Command history available with ↑/↓ in command mode
- All numeric inputs accept hex (0x prefix) or decimal

## Architecture

The VM implements the Ripple architecture as specified in [`docs/arch/`](../docs/arch/README.md). Device MMIO: [`mmio.md`](mmio.md).

### Registers
32 registers: R0 (zero), PC/PCB, RA/RAB, RV0/RV1, A0–A3, X0–X3, T0–T7, S0–S3, SC, SB, SP, FP, GP. Full map: [`docs/arch/registers.md`](../docs/arch/registers.md).

### Memory
- Banked 16-bit data memory; C uses bank 1 globals, bank 2 stack, banks 5+ heap ([`docs/arch/memory.md`](../docs/arch/memory.md))
- Memory-mapped I/O in bank 0, words 0-31 (see `mmio.md`):
  - 0: TTY output
  - 1: TTY ready flag
  - 21-26: interrupt controller (`IRQ_STATUS` … `IRQ_CAUSE`)

### Instruction Set
All opcodes from 0x00 to 0x21 are implemented, including:
- ALU operations (ADD, SUB, AND, OR, XOR, SLL, SRL, SLT, SLTU)
- Immediate operations (ADDI, ANDI, ORI, XORI, LI, SLLI, SRLI)
- Data memory operations (LOAD, STORE)
- Instruction memory copies (LOADC, STORC) — X0..X3 ↔ 4 cells at IMEM[bank][addr]; bank and addr are registers
- Control flow (JAL, JALR, BEQ, BNE, BLT, BGE)
- Extended arithmetic (MUL, DIV, MOD and immediate versions)
- Special (NOP, HALT, BRK)

### BRK Instruction Behavior

The BRK (breakpoint) instruction behaves differently depending on the execution mode:

#### Normal Mode (without -d flag)
- Dumps complete VM state to stderr including:
  - All register values (hex and decimal)
  - First 32 words of memory
  - Current instruction details
- **Halts execution immediately**
- Useful for debugging crashes and inspecting state

#### Debug Mode (with -d flag)
- Prints breakpoint notification
- **Pauses execution** without halting
- Allows continuing with 'c' command or single-stepping
- Acts as a traditional debugger breakpoint

## Program Format

The VM loads binary programs in RLINK format:
- Magic: "RLINK" (5 bytes)
- Entry point (4 bytes, little-endian)
- Instruction count (4 bytes, little-endian)
- Instructions (8 bytes each)
- Data size (4 bytes, little-endian)
- Data section (variable length)

CPU IRQ ABI version 2, optional interrupt-stack switching, and the deterministic
instruction timer are documented in [stacks-and-interrupts.md](../docs/arch/stacks-and-interrupts.md).
Old IRQ binaries require rebuilding; the device mailbox and logical game clock are unchanged.

The same mailbox also provides `HOST_MONOTONIC` and `HOST_REALTIME` (capability
0x1000), returning 64-bit seconds plus nanoseconds at 1 ms resolution. Operating
systems can use elapsed host time for deadlines and Unix UTC time for their
calendar without tying either to CPU speed. These reads do not advance the
deterministic game clock or generate interrupts. See the
[host-clock contract](mmio.md#host-clocks) for checkpoint and replay semantics.
